## 目的・背景

テストコードが増えるにつれて「何が担保されているか・何が足りないか」が見えなくなる。
品質を設計するためには、テストを俯瞰できる構造が必要。

## 問題の構造

現在の流れ：
```
spec.md（機能一覧）→ behavior（振舞）→ test（コード）
```

この一本線では、「specのどの機能がどの振舞で担保されているか」が見えない。
結果として、テストコードの量は増えても品質のリスクが把握できない。

「動かして穴を塞ぐ」式であれば今の構造で十分だが、
「品質を設計する」ならspec起点の樹形図が必要。

## 欲しいもの

spec.mdの機能一覧を起点にして、

- どの機能が
- どの観点で
- テストされているか／いないか（リスクの高低）

が俯瞰できる地図。フェーズごとに樹形図上になっていて、リスクが見えやすい状態。

## 論点

- 地図をどこに置くか（spec.mdに埋め込む・別ファイル・自動生成など）
- behaviorファイルとspec.mdの対応をどう繋げるか
- 管理コストをどう下げるか（手動維持 vs 構造で分かる設計）
- フロントはE2Eの比重が大きいため、E2E中心の地図設計が現実的か

## 次のアクション（未定）

- spec.mdと振舞の対応設計を検討する
- 地図の形式（Markdown表・ツール連携など）を選ぶ
