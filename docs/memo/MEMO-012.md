## 目的・背景

フロントエンド開発における「プロダクト品質」と「プログラム品質」をどう担保するか、
それぞれのフローをどう設計するかを整理するために議論した。

## 論点

- 人間のチェックポイントをどこに置くか
- 単体・結合・E2Eの役割分担
- 「設計」フェーズが必須かどうか
- TDDサイクルと上流との関係

## 出した選択肢・整理

### 2つの品質トラック

- **プロダクト品質**：目的・要件・振舞・E2Eで測る。「作るべきものを作ったか」
- **プログラム品質**：設計・テスト・実装で測る。「正しく作られているか」

### 振舞が橋渡しになる構造

```
目的 → 要件 → 振舞
                ├→ E2Eシナリオ（先に書く、まだ動かない）
                └→ (設計) → 単体/結合テスト → 実装
                                                ↓
                                          E2Eを通す
```

- 振舞から2つのトラックが分岐し、実装完了で合流する
- 設計は複雑さに応じてやるかどうか判断する（シンプルならテストから直接入る）

### テストの担い手

| 担い手 | 対象 |
|--------|------|
| 自動テスト | ロジックの正しさ、決まった操作の結果 |
| 探索的テスト | 想定外の使い方、視認と実動作の一致、感覚的なおかしさ |

- ドラッグ&ドロップのような「視認と実動作の一致」はE2E or 探索的テストで担保
- D&DのE2E自動化は難易度が高い（Playwrightでも再現度にクセあり）

### TDDサイクルの位置づけ

- `設計 → テスト → 実装（Red→Green→Refactor）` が基本サイクル
- 「実装できない」「振舞の定義が曖昧」となったときだけ上流に返す
- 上流への逆流は例外であって通常フローではない

### 思想的な位置づけ

アジャイルの発展形。BDD・TDDの思想を組み込み、AIが設計の副産物を担うことで
人間のチェックポイントを絞る方向を目指す。

### 実装の進め方（2026-03-27追記）

フェーズを「成果物の種類（doc/impl/test）」で区切るより、「実装の深さ」で区切る方が思考の流れに合っている。

```
ハッピーパスを通す → 異常系 → 探索 → リファクタ
```

この順番は自然で、各ステップで「止めるか続けるか」を判断しやすい。

### TDDと人間・Claudeの役割分担（2026-03-27追記）

TDDに縛られすぎることへの懸念：

- **Claudeにとって**：テストを書いてから実装する手順はコストがほぼゼロ。品質担保として機能する
- **人間にとって**：「まずテストを書く」という逆順の思考は認知コストが高い。探索的に作りたい場面では邪魔になる

自然な役割分担：

| 担い手 | 役割 |
|--------|------|
| 人間 | ハッピーパス→異常系→探索→リファクタの流れで方向を決める |
| Claude | TDDの手順を守り、実装の品質を担保する |

人間はフローを決め、Claudeは実装の品質を担保する。

### ドキュメント・issueの使い分け（2026-03-27追記）

- **GitHub issue** → 議論・提案・意思決定。ロードマップ・方針レベルのもの。長期化・重要度が高いものだけ上げる
- **docs/memo/** → issueに置けない粒度のメモ。一時置き場。他ドキュメントに昇格したら削除
- **docs/decisions/** → 確定した意思決定のADR

```
memo/ に書く
  → 議論が長期化・重要度が高い → issueに昇格
  → 他ドキュメントに統合できた → memo/から削除
```

`docs/ideas/` は `docs/memo/` に統合する方向。
