# ADR-001: 開発フロー・ステータス定義

## 決定事項

### 開発フロー

```
目的・アイデア
  ↓
要件（spec.md）
  ↓
設計（design.md・schema・API定義）
  ↓
振舞（FB-XXX.md）← ここまでがドキュメントフェーズ
  ↓
単体テスト作成 → Red確認
  ↓
実装 → Green確認
  ↓
結合テスト作成 → Red確認
  ↓
結合実装 → Green確認
  ↓
E2Eテスト作成 → Red確認
  ↓
E2E確認（Playwright）
```

### GitHub Projectsカラムとの対応

| カラム | 意味 |
|--------|------|
| Backlog | 目的・アイデア段階。spec未承認 |
| Ready | spec・設計・振舞がすべて`approved` |
| In progress | テスト〜実装中 |
| Blocked | 実装中に仕様の疑問が出て止まっている |
| In review | PR提出・レビュー待ち |
| Done | マージ済み |

### ステータス定義

ドキュメント全般のfrontmatterに記載する。

| status | 意味 | 次のアクション |
|--------|------|--------------|
| `idea` | アイデア段階。議論すらしていない | 議論する |
| `discussing` | 議論中。方向性を探っている | 方向性を決める |
| `draft` | 方向性は決まった。詳細を詰めている | 詳細を固めてapprovedへ |
| `approved` | 確定。実装に進める | 下位フェーズへ |
| `sleeping` | 一旦寝かせ。将来再検討 | 再検討のタイミングを待つ |
| `deprecated` | 廃止 | — |

### ステータスとAgentの関係

- `idea` / `discussing` / `sleeping` のドキュメントに対して、Agentは実装の提案をしない
- `approved` になって初めて、下位フェーズ（振舞・テスト・実装）に進める
- Agentは現在のステータスを必ず確認してから作業を始める

## 議論の経緯

### なぜステータスを拡張したか
- `draft → approved` だけでは「議論中」「寝かせ中」が表現できなかった
- AI駆動開発では、アイデアを練っている段階で「これで実装していいですか？」と聞かれることが煩わしい
- ステータスを明示することで、Agentが余計な提案をしてくる状況を防ぐ

### Blockedカラムを追加した理由
- 実装中に仕様の疑問が出たとき、元IssueをBacklogに戻すと「なぜ戻ったか」が埋もれる
- 別Issueを起票して`Blocked by #XX`で紐づけることで、議論の経緯が追える
- 元IssueはBlockedカラムで止まっていることが一目でわかる

### なぜADRを導入したか
- 議論の背景・却下した選択肢を残さないと、後から「なぜこうなったか」がわからなくなる
- ドキュメントに決定事項だけでなく、議論の経緯を残すことで、将来の意思決定の参考にする
