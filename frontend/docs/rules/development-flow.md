# 開発フロー

## 2つの品質トラック

- **プロダクト品質**：目的・要件・振舞・E2Eで測る。「作るべきものを作ったか」
- **プログラム品質**：設計・テスト・実装で測る。「正しく作られているか」

## フロー構造

```
目的 → 要件 → 振舞
                ├→ E2Eシナリオ（先に書く、まだ動かない）
                └→ (設計) → 単体/結合テスト → 実装
                                                ↓
                                          E2Eを通す
```

- 振舞が2つのトラックの起点（橋渡し）になる
- 実装完了でE2Eが通り、2トラックが合流する

## 設計フェーズの扱い

設計は必須ではない。複雑さに応じて判断する。

- シンプルな振舞 → テストから直接入る
- データの流れ・アーキテクチャの考慮が必要な場合 → 設計を挟む

## TDDサイクル

`設計 → テスト → 実装（Red → Green → Refactor）` を基本サイクルとする。

- 「実装できない」「振舞の定義が曖昧」となったときだけ上流に返す
- 上流への逆流は例外であって通常フローではない

## テストの担い手

| 担い手 | 対象 |
|--------|------|
| 自動テスト | ロジックの正しさ、決まった操作の結果 |
| 探索的テスト | 想定外の使い方、視認と実動作の一致、感覚的なおかしさ |

「視認と実動作の一致」が求められる操作（D&Dなど）は、自動化が困難なケースがある。
その場合は探索的テストで担保する。

## 人間のチェックポイント

現時点では試行錯誤の段階。「どんな指示・CLAUDE.mdであれば良い品質か」の感覚を
積み上げてからチェックポイントを絞る。
